# План истории 2.1 — Жизненный цикл прогулки и восстановление сессии

Эпик: epic-walk-tracking · Тикет: 2.1 (tickets.toml) · Дата: 2026-10-09
Статус: план перед сборкой. Ссылки: FR-5, AD-5, AD-4; база — TrackJournal/PointFilter (1.7), TrackHistory (свеча).

## Что строим

Модель сессии прогулки (полный жизненный цикл) + её персистентность + восстановление
после убийства процесса + агрегаты в чистом Kotlinе + минимальная интеграция в UI.

## Решения по размещению

- `tracking/WalkSession.kt` — модель сессии (чистый JVM, как TrackJournal/PointFilter).
  Это domain-логика записи: UI/сервис только вызывают переходы, ничего не вычисляют
  (AD-4). Пакет `domain` не импортируется ради избежания domain↔tracking-цикла:
  агрегаты сессии не трогают ни туман, ни регионы.
- `tracking/WalkSessionStore.kt` — файловое хранилище снимка сессии
  (`session/session.json`): save = tmp-файл + fsync + rename (атомарность против
  убийства процесса посреди записи), load с formatVersion.
- sessionId = epochMillis старта = имя журнала `track-<id>.track` (конвенция
  TrackingService/TrackHistory): сессия и её журнал — 1:1, поиск журнала не гадает.

## Модель (WalkSession)

- Состояния: `ACTIVE → PAUSED → ACTIVE → FINISHED`; FINISHED — терминальное.
- Переходы возвращают sealed-результат (Ok/InvalidTransition — Consistency Conventions),
  невалидные переходы состояние не двигают.
- `acceptPoint(lat, lon, t)` — только в ACTIVE; дистанция — haversine от последней
  ПРИНЯТОЙ точки (переиспользуем haversineMeters из TrackModels). Отвергнутые фильтром
  точки сюда не доходят (решает сервис по вердикту PointFilter) — модель про честные
  точки только.
- `pause(now)`/`resume(now)` — интервалы пауз в списке; открытая пауза — полем.
- `finish(now)` — в ACTIVE/PAUSED; открытую паузу закрывает.
- Агрегаты: `distanceMeters` (только принятые), `acceptedCount`,
  `activeMillis(now)` = (now − startedAt) − Σпаузы − открытая пауза. Форматирование
  («км», «мин») — только UI.

## Восстановление (AD-5)

- Сервис при ACTION_START читает store: есть незавершённая сессия (ACTIVE/PAUSED) и
  журнал `track-<sessionId>.track` на диске → восстановление: replay журнала через
  PointFilter (startedAt из заголовка, как TrackHistory) → принятые точки заново
  проходят session.acceptPoint → якорь фильтра и агрегаты восстановлены детерминированно;
  запись продолжается в ТОТ ЖЕ журнал (append). Потеря — секунды между последним
  fsync и убийством, не прогулка.
- Незавершённой сессии нет → новая сессия + новый журнал (текущее поведение).
- ACTION_STOP → finish(now) + store.save(FINISHED) + шина публикует итог.
- Хвост из 1.13 (восстановление тропы после реального перезапуска) закрывается
  тем же механизмом — журнал дописывается, TrackHistory подхватит при запуске.

## Шина и UI

- TrackingSnapshot: + `walkState` (ACTIVE/PAUSED/FINISHED как строка-enum или Boolean
  пары), + `walkDistanceMeters`, + `walkActiveMillis`; метод `walkStatsUpdated(...)`.
  Публикуется сервисом на каждой принятой точке и на переходах.
- MapUiState: + те же три поля (из шины). MapScreen: строка состояния
  «Идёт прогулка · X,X км · N мин» вместо «Идёт запись», кнопка «Завершить прогулку»
  (ACTION_STOP — без новых action'ов; пауза приходит в 2.4). Форматирование — в UI.

## Тесты (JVM)

- WalkSessionTest: переходы (все допустимые и запрещённые), дистанция по принятым
  (отвергнутая между двумя принятыми дистанцию не раздувает — через пропуск точки),
  чистое время с паузами (в т.ч. открытая пауза), finish закрывает открытую паузу.
- WalkSessionStoreTest: save/load круглый, formatVersion, битый файл → null/Invalid,
  tmp+rename не оставляет .tmp-мусора, незавершённая vs FINISHED.
